Davai / JUCE 8 / C++20 / acid synthesizer

Davai

Davai is a synthesizer built around a virtual analog filter: an emulation of the TB-303's diode ladder, the squelchy, resonant heart of acid. The filter is custom code, written by hand. It's solved sample by sample with zero-delay feedback and nonlinear resonance, and runs at 4× oversampling. Its math comes from Vadim Zavalishin's book The Art of VA Filter Design and Will Pirkle's application notes Virtual Analog Diode Ladder Filter (App Note 6) and Virtual Analog (VA) Filter Implementation and Comparisons (App Note 4).

Around the filter: oscillators, envelopes, three LFOs (including a Lorenz chaos mode), a modulation matrix, an arpeggiator, a piano-roll sequencer, a full effects chain, and factory presets to start from. The rest of the instrument and its interface was built through a careful, iterative process of AI-assisted "vibe coding": every part was tried, played and refined until it felt right.

Davai runs as a VST3 and Audio Unit plugin on Mac, as a VST3 on Windows, and as a standalone app on iPad.

  • macOS (VST3 + Audio Unit, Apple Silicon & Intel)
  • Windows (VST3, 64-bit)
  • iPad (beta, via TestFlight)

Conception

Where it comes from

The Roland TB-303 Bass Line came out in 1981 as a practice box for guitarists, and was dropped in 1984 after about 10,000 units. A few years later, Chicago producers pushed its resonant filter hard, and it became the sound of acid house.

Davai follows the 303's circuit, using the published analysis of the Devil Fish, Robin Whittle's hardware mod of the 303. Where the Devil Fish manual gives a real value, Davai uses it: the 200 ms to 2 s filter decay, the fixed 200 ms decay on accented notes, and the 22 ms slide (a 100 kΩ resistor charging a 0.22 µF capacitor). Values with no source are marked as estimates in the design notes.

The other half of Davai's inspiration is the Novation Bass Station II, a modern analog mono synth that also has a 303-style "Acid" diode filter. Davai takes its broader voice architecture from it:

  • Voice: two oscillators, a sub oscillator, noise and a ring modulator, mixed before the filter.
  • Filter choice: a classic transistor ladder alongside the acid diode ladder.
  • Osc Filter Mod: the second oscillator can modulate the filter's cutoff at audio rate, for growling, metallic tones.
  • Signal path: Davai follows the same order, filter first, then the amplifier stage.

So Davai sits between the two machines: the 303's circuit and its slide-and-accent phrasing, inside a richer, Bass Station-style synth voice.

Environment and Tooling
  • Language: C++20, built with CMake and JUCE 8 (as a git submodule).
  • Formats: VST3 and AU on macOS, VST3 on Windows, standalone app on iPad.
  • Tests: JUCE unit tests run with CTest. The DSP classes are plain C++ so they can be tested on their own.
  • CI: GitHub Actions, with clang-format checks, build, and tests.
  • Installers: a signed and notarized macOS installer, and a Windows installer made with Inno Setup.

Architecture

The sound follows the 303's own path: Oscillators -> Filter -> Amp envelope -> Effects. Each part of the original circuit has its own class:

  • Oscillator: the 303's oscillator, one phase ramp with a saw or square output. PolyBLEP smooths the hard edges to avoid aliasing. A second oscillator, a sub oscillator, and noise are added on top.
  • TB303DiodeFilter: the hand-written diode ladder filter, run at 4× oversampling. A transistor ladder is also available.
  • AttackDecayEnvelope: the 303's filter envelope. Like the hardware, it ignores note-off and always finishes its decay.
  • AdsrEnvelope: the amp envelope. The 303's was fixed; this one is a full ADSR with editable curves.
  • Accent: two separate envelopes, one boosting the volume and one sweeping the filter, as in the real circuit.
  • PitchGlide: the slide between notes, modeled as the same simple RC lag as the hardware.
  • StepSequencer and PianoRollSequencer: patterns with real accent and slide flags on each step or note. From a MIDI keyboard, accent comes from velocity and slide from playing legato.
  • LfoModulationMatrix and ModEnvelopeMatrix: three LFOs and a modulation envelope can each drive any parameter. Their effects add up instead of overriding each other.
  • Effects: nine stages (two filters, saturation, distortion, chorus, delay, EQ, compressor, reverb) in an order you can change.

Audioviz / JUCE 8 / C++20 / audio visualization

Audioviz

Audioviz is a plugin and standalone app that give tools to analyse audio. It combines oscilloscope-style waveform display, spectrum analysis, trigger controls, metering, zoom, and time-window navigation in a compact audio tool.

The core challenge is keeping the audio thread safe while the UI remains fluid. Incoming samples are written into real-time history buffers, then copied into stable snapshots for drawing so the visual layer can stay responsive without blocking audio processing.

Environment and Tooling

Built as a modern JUCE audio project in C++20, using CMake 3.22 and a JUCE submodule, coded both by hand and with AI assistance. The CMake project defines versioned build information, shared sources for plugin and standalone targets, optional ccache, and test discovery through CTest.

  • Language: C++20, with extensions disabled.
  • Frameworks: JUCE audio, GUI, DSP, events, and standalone/plugin wrappers.
  • Build: CMake release build with generated JUCE headers and shared source lists.
  • Targets: standalone app plus plugin formats such as VST3 and AU.
  • CI: GitHub Actions on macOS, with submodules, ccache, clang-format checks, CMake build, and CTest.

Architecture

The application is organized around a strict separation between the real-time audio path, analysis state, rendering, and interaction code: audio input -> PluginProcessor -> ScopeData/SpectrumData -> UI renderers. This keeps the audio callback predictable while letting the interface repaint at its own rhythm.

  • Source/Audio: owns the processor, waveform history, trigger logic, meters, and spectrum analysis. These classes isolate sample capture and analysis from drawing code.
  • ScopeWaveformHistory: stores incoming samples in per-channel circular buffers so the UI can copy stable snapshots without blocking the audio thread.
  • ScopeData and SpectrumData: expose prepared data for the waveform and frequency views, which keeps renderers simple and avoids recomputing expensive values in paint calls.
  • Source/State: centralizes parameter/state handling so processor and UI agree on time windows, trigger mode, spectrum settings, and display choices.
  • Source/UI/Renderers: contains focused drawing components for waveform, grid, clipping, spectrum, meters, and titles; each renderer has one visual responsibility.
  • Source/UI/Interaction: isolates drag, wheel, and zoom behavior from rendering so input logic can evolve without touching DSP or drawing internals.
  • Source/UI/Panels and controls: compose the toolbar and parameter panels from smaller controls, making the editor layout easier to maintain.

Short time windows keep precise raw sample history for trigger-aligned oscilloscope drawing. Longer time windows use min/max overview storage so broad waveform shape can be drawn efficiently without scanning every stored sample on each repaint.

visualAPI / Python 3.14 / ModernGL / GLSL / generative visuals

Visual API

Visual API turns my archive of Processing sketches into a Python library of real-time visuals. Each sketch becomes a Python object that can be listed, searched and launched in one line, like visualAPI.BlackHole1(seconds=30), and is drawn on the GPU with ModernGL and GLSL shaders.

The archive holds 250 sketches, and every one of them is in the catalog from the start. So far 67 have been ported, family by family: particle orbits, 3D wave surfaces, image ripples, mountains, lit oyster shells and circle compositions. There are also 7 original visuals with no Processing source: cellular automata (Conway's Life, HighLife, Seeds, Bloom and the continuous Lenia) and AImmune, an audio-reactive immune-system simulation that grows a reaction-diffusion pattern.

A gallery mode plays the visuals one after another with crossfades, in a window or fullscreen, and can record a full cycle to an MP4 movie.

Environment and Tooling

  • Language: Python 3.14, in a Conda environment.
  • Libraries: NumPy, ModernGL, GLFW, GLSL shaders and Pillow, with ffmpeg for movie export.
  • Tests and quality: pytest, Ruff and strict mypy. The tests never open a GPU window, so they run anywhere.
  • CI: GitHub Actions running Ruff format and lint checks, mypy and pytest.

audiovisual / Python / ModernGL / GLSL

Music Visualizer

Music Visualizer is a real-time audio-reactive visual engine. Python extracts deterministic audio features from live input, maps them to visual parameters, then sends those parameters to GLSL shaders.

Conception

Listening to the music

Many times per second, the engine takes a short window of the incoming sound and measures a few simple things about it:

  • Loudness (RMS): how strong the sound is overall.
  • Bass, mids and highs: how much energy sits in the low (20–250 Hz), middle (250 Hz–4 kHz) and high (4–20 kHz) frequencies.
  • Brightness (spectral centroid): whether the sound leans dark or bright.
  • Onset: a sudden rise in volume, like the start of a note or a hit.
  • Kick: a sudden rise in the bass, to catch the kick drum.

These values are smoothed over time: they rise fast and fall slowly, so the image reacts at once but doesn't flicker. The kick gets its own envelope, so each hit gives a clear punch.

From sound to image

The features are then mixed into eight visual parameters, each one driven by a few features:

  • Scale (bass and kick): the shape swells with the low end.
  • Deformation (bass and kick): how much the shape bends and flows.
  • Pulse (kick, loudness and onsets): the beat of the image.
  • Intensity (loudness, mids and kick): how much is going on.
  • Hue (brightness and highs): the color drifts with the timbre.
  • Detail (highs and mids): fine texture and sparks.
  • Flash (kick and onsets): a burst of light on each hit.
  • Kick: passed straight through for shockwaves and bursts.

Each shader reads the same parameters in its own way. The particle shader turns them into bursts and sparks, the fluid shader into pressure and flow. A playlist can crossfade between shaders while the music plays, as in the video above.

Environment and Tooling

Built as a Python audio-visual engine with a Conda environment and a typed/linted package layout. Python handles live audio capture, feature extraction, mapping, and orchestration, while ModernGL and GLSL handle the real-time visual output.

  • Language: Python 3.14.6, with Ruff targeting Python 3.14 and mypy checking src and tests.
  • Frameworks and libraries: NumPy, SciPy, sounddevice, ModernGL, GLFW, GLSL shaders.
  • Build/environment: Conda environment in environment.yml plus pyproject.toml tooling configuration.
  • Testing and quality: pytest tests, Ruff format/lint, and strict mypy options.
  • CI: GitHub Actions on macOS running Conda setup, Ruff format check, Ruff lint, mypy, and pytest.
