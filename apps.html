Audioviz / JUCE 8 / C++20 / audio visualization

Audioviz

Audioviz is a real-time audio visualization plugin and standalone app focused on making waveforms, levels, and frequency content readable at musical speed. It combines oscilloscope-style waveform display, spectrum analysis, trigger controls, metering, zoom, and time-window navigation in a compact audio tool.

The core challenge is keeping the audio thread safe while the UI remains fluid. Incoming samples are written into real-time friendly history buffers, then copied into stable snapshots for drawing so the visual layer can stay responsive without blocking audio processing.

Conception

Environment and Tooling

Built as a modern JUCE audio project in C++20, using CMake 3.22 and a JUCE submodule. The CMake project defines versioned build information, shared sources for plugin and standalone targets, optional ccache, and test discovery through CTest.

  • Language: C++20, with extensions disabled.
  • Frameworks: JUCE audio, GUI, DSP, events, and standalone/plugin wrappers.
  • Build: CMake release build with generated JUCE headers and shared source lists.
  • Targets: standalone app plus plugin formats such as VST3 and AU.
  • CI: GitHub Actions on macOS, with submodules, ccache, clang-format checks, CMake build, and CTest.

Code snippet

void ScopeWaveformHistory::pushSamples(
    const juce::AudioBuffer<float>& buffer,
    int numInputChannels)
{
    readWriteStatus.fetch_add(1, std::memory_order_acq_rel);
    auto writePosition = scopeWritePosition.load(std::memory_order_relaxed);

    for (auto sample = 0; sample < buffer.getNumSamples(); ++sample)
    {
        for (auto channel = 0; channel < channelsToStore; ++channel)
        {
            const auto storageIndex = channel * scopeSize + writePosition;
            scopeSamples[storageIndex].store(
                buffer.getSample(channel, sample),
                std::memory_order_relaxed);
        }

        writePosition = (writePosition + 1) % scopeSize;
    }

    scopeWritePosition.store(writePosition, std::memory_order_release);
    readWriteStatus.fetch_add(1, std::memory_order_release);
}

The samples are stored in per-channel rings. The UI checks the read/write status before and after copying; if the audio thread writes during the copy, the UI discards that snapshot and tries again.

Architecture

The application is organized around a strict separation between the real-time audio path, analysis state, rendering, and interaction code: audio input -> PluginProcessor -> ScopeData/SpectrumData -> UI renderers. This keeps the audio callback predictable while letting the interface repaint at its own rhythm.

  • Source/Audio: owns the processor, waveform history, trigger logic, meters, and spectrum analysis. These classes isolate sample capture and analysis from drawing code.
  • ScopeWaveformHistory: stores incoming samples in per-channel circular buffers so the UI can copy stable snapshots without blocking the audio thread.
  • ScopeData and SpectrumData: expose prepared data for the waveform and frequency views, which keeps renderers simple and avoids recomputing expensive values in paint calls.
  • Source/State: centralizes parameter/state handling so processor and UI agree on time windows, trigger mode, spectrum settings, and display choices.
  • Source/UI/Renderers: contains focused drawing components for waveform, grid, clipping, spectrum, meters, and titles; each renderer has one visual responsibility.
  • Source/UI/Interaction: isolates drag, wheel, and zoom behavior from rendering so input logic can evolve without touching DSP or drawing internals.
  • Source/UI/Panels and controls: compose the toolbar and parameter panels from smaller controls, making the editor layout easier to maintain.

Short time windows keep precise raw sample history for trigger-aligned oscilloscope drawing. Longer time windows use min/max overview storage so broad waveform shape can be drawn efficiently without scanning every stored sample on each repaint.

Music Visualizer

Music Visualizer is a real-time audio-reactive visual engine. Python extracts deterministic audio features from live input, maps them to visual parameters, then sends those parameters to GLSL shaders.

Good images here would be stills from the particle and fluid shader presets, plus a short screen recording exported as a poster frame.

Shader still image

Conception

Environment and Tooling

Built as a Python audio-visual engine with a Conda environment and a typed/linted package layout. Python handles live audio capture, feature extraction, mapping, and orchestration, while ModernGL and GLSL handle the real-time visual output.

  • Language: Python 3.14.6, with Ruff targeting Python 3.14 and mypy checking src and tests.
  • Frameworks and libraries: NumPy, SciPy, sounddevice, ModernGL, GLFW, GLSL shaders.
  • Build/environment: Conda environment in environment.yml plus pyproject.toml tooling configuration.
  • Testing and quality: pytest tests, Ruff format/lint, and strict mypy options.
  • CI: GitHub Actions on macOS running Conda setup, Ruff format check, Ruff lint, mypy, and pytest.

Code snippet

def compute_kick(signal, sample_rate):
    split = signal.size // 2
    previous_bass = compute_frequency_bands(
        signal[:split], sample_rate)["bass"]
    current_bass = compute_frequency_bands(
        signal[split:], sample_rate)["bass"]

    growth = max(0.0, current_bass - previous_bass)
    kick = current_bass * 0.65 + growth * 0.35
    return float(np.clip(kick, 0.0, 1.0))

This feature estimates a kick by combining current bass energy with low-frequency growth between the first and second half of the audio window.

The shader turns audio features into visible structure: bass inflates the body, kick expands a shell, highs add detail, and flash brightens the transient.

Architecture

The project is organized as a pipeline: Live Audio -> Audio Engine -> Feature Extraction -> Feature Mapping -> Visual Parameters -> ModernGL Renderer -> GLSL Shaders -> Display. Each step has a narrow responsibility, which makes the visual behavior easier to tune without rewriting capture or rendering code.

  • src: contains the Python runtime for audio input, signal analysis, visual parameter mapping, and renderer orchestration.
  • config: keeps tunable values outside the code so mapping constants, visual presets, and runtime settings can change without editing the engine.
  • shaders: stores GLSL programs. The renderer sends normalized audio features as uniforms, and the shader turns those values into motion, color, and shape.
  • docs: documents the pipeline and design notes so the project remains understandable as experiments accumulate.
  • tests: protects deterministic feature extraction and mapping behavior, which is important because visual quality depends on stable signal interpretation.

The deterministic mapping layer is deliberately separate from rendering: it can later be replaced by a learned or preset-based mapper while the shader interface stays stable.

Zavalishin / JUCE 8 / C++20 / acid synthesizer

Davai

Davai is a synthesizer built around a virtual analog filter: an emulation of the TB-303's diode ladder, the squelchy, resonant heart of acid. The filter is custom code, written by hand. It's solved sample by sample with zero-delay feedback and nonlinear resonance, and runs at 4× oversampling. Its math comes from Vadim Zavalishin's book The Art of VA Filter Design and Will Pirkle's application notes Virtual Analog Diode Ladder Filter (App Note 6) and Virtual Analog (VA) Filter Implementation and Comparisons (App Note 4).

Around the filter: oscillators, envelopes, three LFOs (including a Lorenz chaos mode), a modulation matrix, an arpeggiator, a piano-roll sequencer, a full effects chain, and factory presets to start from. The rest of the instrument and its interface was built through a careful, iterative process of AI-assisted "vibe coding": every part was tried, played and refined until it felt right.

Davai runs as a VST3 and Audio Unit plugin on Mac, as a VST3 on Windows, and as a standalone app on iPad.

  • macOS (VST3 + Audio Unit, Apple Silicon & Intel)
  • Windows (VST3, 64-bit). Windows may show "Unknown publisher": click More info → Run anyway.

Conception

Where it comes from

The Roland TB-303 Bass Line came out in 1981 as a practice box for guitarists, and was dropped in 1984 after about 10,000 units. A few years later, Chicago producers pushed its resonant filter hard, and it became the sound of acid house.

Davai follows the 303's circuit, using the published analysis of the Devil Fish, Robin Whittle's hardware mod of the 303. Where the Devil Fish manual gives a real value, Davai uses it: the 200 ms to 2 s filter decay, the fixed 200 ms decay on accented notes, and the 22 ms slide (a 100 kΩ resistor charging a 0.22 µF capacitor). Values with no source are marked as estimates in the design notes.

Environment and Tooling
  • Language: C++20, built with CMake and JUCE 8 (as a git submodule).
  • Formats: VST3 and AU on macOS, VST3 on Windows, standalone app on iPad.
  • Tests: JUCE unit tests run with CTest. The DSP classes are plain C++ so they can be tested on their own.
  • CI: GitHub Actions, with clang-format checks, build, and tests.
  • Installers: a signed and notarized macOS installer, and a Windows installer made with Inno Setup.

Code snippet

for (int i = 0; i < maxIterations; ++i)
{
    const float t = std::tanh(Gamma * u + sigma);
    const float F = u - x + k * t;
    const float Fprime = 1.0f + k * Gamma * (1.0f - t * t);

    if (std::abs(F) <= residualTolerance)
        break;

    if (F < 0.0f)
        lo = u;
    else
        hi = u;

    const float newtonU = u - F / Fprime;
    const bool safeNewton = std::isfinite(newtonU)
        && newtonU > lo && newtonU < hi;

    u = safeNewton ? newtonU : 0.5f * (lo + hi);
}

The filter's resonance feeds its output back into its input, so each sample depends on itself. This loop solves that equation inside the same sample, with the tanh giving the diodes their saturation. It uses Newton's method, but keeps the answer inside a known range and falls back to halving that range when a Newton step would jump out. That way it always converges, even at high resonance.

Architecture

The sound follows the 303's own path: Oscillators -> Filter -> Amp envelope -> Effects. Each part of the original circuit has its own class:

  • Oscillator: the 303's oscillator, one phase ramp with a saw or square output. PolyBLEP smooths the hard edges to avoid aliasing. A second oscillator, a sub oscillator, and noise are added on top.
  • TB303DiodeFilter: the hand-written diode ladder filter, run at 4× oversampling. A transistor ladder is also available.
  • AttackDecayEnvelope: the 303's filter envelope. Like the hardware, it ignores note-off and always finishes its decay.
  • AdsrEnvelope: the amp envelope. The 303's was fixed; this one is a full ADSR with editable curves.
  • Accent: two separate envelopes, one boosting the volume and one sweeping the filter, as in the real circuit.
  • PitchGlide: the slide between notes, modeled as the same simple RC lag as the hardware.
  • StepSequencer and PianoRollSequencer: patterns with real accent and slide flags on each step or note. From a MIDI keyboard, accent comes from velocity and slide from playing legato.
  • LfoModulationMatrix and ModEnvelopeMatrix: three LFOs and a modulation envelope can each drive any parameter. Their effects add up instead of overriding each other.
  • Effects: nine stages (two filters, saturation, distortion, chorus, delay, EQ, compressor, reverb) in an order you can change.

The DSP lives in Source/Audio, the parameters in Source/State, and the interface in Source/UI, with one panel per section of the synth.

Klide / JUCE 7 / C++17 / older project

Klide

Klide is an older Euclidean rhythm drum-machine VST3. It can run four sample sequences and distribute pulses across a fixed number of steps with the Bjorklund algorithm. It is a meaningful early project, but it needs refactoring: clearer naming, modern JUCE/CMake structure, tests, and separation between sequencing, audio, and UI state.

Klide interface image

Conception

Environment and Tooling

Klide is an older JUCE project created with Projucer rather than the newer CMake/JUCE layout used by the later apps. It is useful as a historical project, but its build and organization need modernization.

  • Language: C++17-era JUCE code.
  • Frameworks: JUCE plugin framework, with a Klide.jucer Projucer project file.
  • Build: generated from Projucer rather than a checked-in CMake pipeline.
  • Targets: VST3 drum-machine plugin workflow.
  • CI: no GitHub Actions workflow found in the repository.
  • Refactor target: migrate to CMake/JUCE, add tests, and separate sequencer, sampler, DSP, state, and editor code.

Code snippet

do {
    count_[level] = divisor / remainder_[level];
    remainder_[level + 1] = divisor % remainder_[level];
    divisor = remainder_[level];
    level = level + 1;
} while (remainder_[level] > 1);

count_[level] = divisor;
build_string(level, reverse);

Bjorklund's algorithm repeatedly divides rests by pulses to create the most even distribution possible. For example, 5 pulses over 16 steps becomes a rhythm where the gaps are balanced rather than clustered.

Architecture

Klide combines several responsibilities that should now be separated: Euclidean sequence generation -> sample triggering -> voice/playback state -> plugin parameters -> editor controls. The current structure works as a compact early plugin, but the refactor goal is to give each part a clear boundary.

  • Sequencer generation: the Bjorklund algorithm builds evenly distributed rhythms from pulses and steps. This should become a pure, tested module with no UI dependency.
  • Timing and triggering: converts generated patterns into sample triggers synchronized to the plugin timeline.
  • Sampler/playback layer: loads and plays drum samples, ideally separated from sequencing so the same rhythm engine can drive other sound sources.
  • Envelope and filter controls: shape each sample voice; these should live with DSP/voice state rather than editor widgets.
  • Plugin state: stores parameters and pattern settings for host automation and preset recall.
  • Editor: should become a view/controller over the sequencer and sampler state, including drag-and-drop sample loading and per-track controls.

The reason to refactor is not cosmetic: Euclidean rhythm generation is a valuable core idea, and isolating it would make the app testable, easier to extend, and easier to port to the modern JUCE/CMake structure.
